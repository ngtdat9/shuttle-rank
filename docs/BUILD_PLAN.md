# Badminton Club Ranking App --- Cursor Build Plan

> **Project goal:** Build a small, public, shareable badminton ranking
> website for a private group of 6--10 friends.
>
> **Chosen database approach (Option A):** Develop locally with
> **SQLite + SQLAlchemy + Alembic**, then deploy with **Supabase
> PostgreSQL** when the app is ready for public access.
>
> **Build philosophy:** Keep the application simple and modular. This is
> a small club app, not a large-scale sports platform. Build and test
> one module at a time.

------------------------------------------------------------------------

## 1. Product requirements

### 1.1 Users and permissions

There are two kinds of visitors:

  -----------------------------------------------------------------------
  Role                                Access
  ----------------------------------- -----------------------------------
  Public visitor                      Can view all public pages without
                                      logging in

  Admin                               Logs in with email and password;
                                      can manage players, matches,
                                      tournaments, and achievements
  -----------------------------------------------------------------------

-   Anyone with the website link can view public information.
-   There is only one administrator initially: the project owner.
-   Do not provide public registration.
-   Public visitors must not be able to create, edit, or delete records.
-   Enforce admin permissions in the backend. Hiding admin buttons in
    the frontend is not security.
-   Do not expose database credentials, Supabase service-role keys, or
    admin secrets in browser code.

### 1.2 Sport and ranking rules

-   Sport: men's singles badminton.
-   Initial group size: 6--10 players.
-   Matches are played approximately weekly.
-   Match pairings are random or manually arranged by the group.
-   Ranking system: Elo only. Do not implement BWF tournament points.
-   Starting rating: **1500**.
-   Initial K-factor: **32**.
-   Only completed/confirmed matches affect ratings.
-   Canceled or disputed matches do not affect ratings.
-   Tournament matches use the same Elo calculation as ordinary matches.
    No extra tournament bonus.
-   Initially, the result is based only on the match winner. Do not use
    score margin.

### 1.3 Features

**Public pages** - Dashboard and current leaderboard - Player directory
and player profiles - Match history - Head-to-head comparison -
Tournament list and tournament brackets - Monthly leaderboard /
historical monthly snapshots - Rating progression charts - Player
achievements and badges

**Admin features** - Create, edit, and deactivate players - Record match
results - Correct or cancel a match - Create tournaments and add
participants - Generate and manage tournament brackets - Create and
award achievements - View administrative audit history

Do not allow manual editing of a player's Elo rating. Ratings must be
generated by the match-processing service.

### Important distinction

-   **SQLite** is the actual local database.
-   **SQLAlchemy** is the Python ORM used to communicate with SQLite or
    PostgreSQL.
-   **Alembic** manages database schema migrations.
-   **DbVisualizer** is an optional database GUI; it is not a database.

Use SQLAlchemy models and portable SQL wherever practical. Avoid
SQLite-only SQL features in application business logic so the app can
move to PostgreSQL with minimal changes.

## 3. High-level architecture

``` text
Public browser
    |
    v
Next.js frontend ----------------------+
    |                                  |
    | Public GET requests              | Admin requests with access token
    v                                  v
FastAPI backend <----------------------+
    |
    +--> Authentication / authorization
    |
    +--> Player service
    +--> Match service
    +--> Elo rating service
    +--> Ranking/statistics service
    +--> Tournament service
    +--> Achievement service
    |
    v
SQLAlchemy
    |
    +--> SQLite (local development)
    |
    +--> PostgreSQL (production)
```

### Architecture rules

1.  Use a **modular monolith**, not microservices.
2.  The backend owns all business rules and all Elo calculations.
3.  The frontend displays data and sends user actions to the API.
4.  Do not calculate or mutate ratings in the frontend.
5.  Keep database access inside backend models/repositories/services;
    avoid database logic inside route handlers.
6.  Validate all incoming data with Pydantic schemas.
7.  Keep public read endpoints separate from admin write endpoints.
8.  Use UTC timestamps in storage.
9.  Use database transactions for match result processing and rating
    updates.
10. Keep an audit log for administrative changes.

## 5. Database design

Start with these tables. Add fields only when a real feature requires
them.

### 5.1 `players`

  Column             Type / notes
  ------------------ -----------------------
  `id`               UUID primary key
  `display_name`     Required
  `avatar_url`       Nullable
  `current_rating`   Integer, default 1500
  `highest_rating`   Integer, default 1500
  `is_active`        Boolean, default true
  `created_at`       UTC timestamp
  `updated_at`       UTC timestamp

Do not permanently delete a player who has match history. Deactivate the
player instead.

### 5.2 `matches`

  -----------------------------------------------------------------------
  Column                              Type / notes
  ----------------------------------- -----------------------------------
  `id`                                UUID primary key

  `player_a_id`                       FK to players

  `player_b_id`                       FK to players

  `winner_id`                         FK to players

  `match_date`                        When the match was played

  `status`                            `completed`, `canceled`, or
                                      `disputed`

  `tournament_id`                     Nullable FK to tournaments

  `game_scores`                       Optional JSON for game scores,
                                      e.g. `[[21,18],[18,21],[21,15]]`

  `notes`                             Optional

  `created_by`                        Admin identifier

  `created_at`                        UTC timestamp

  `updated_at`                        UTC timestamp
  -----------------------------------------------------------------------

Constraints: - Player A and Player B must be different. - Winner must be
one of the two participants. - A canceled or disputed match must not
affect ratings. - Validate all constraints in the backend and, where
practical, the database.

### 5.3 `rating_history`

  Column            Type / notes
  ----------------- --------------------------
  `id`              UUID primary key
  `player_id`       FK to players
  `match_id`        FK to matches
  `old_rating`      Rating before this match
  `new_rating`      Rating after this match
  `rating_change`   Signed change
  `created_at`      UTC timestamp

Add a unique constraint on `(match_id, player_id)` so a match cannot
accidentally create duplicate rating events for a player.

Treat rating history as an audit trail. Do not silently overwrite
historical rating events.

### 5.4 `monthly_rankings`

Stores end-of-month snapshots. Monthly ranking is a historical view, not
a monthly rating reset.

Suggested columns: - `id` - `player_id` - `year` - `month` - `rating` -
`rank` - `wins` - `losses` - `rating_change_during_month` - `created_at`

Add a unique constraint on `(player_id, year, month)`.

### 5.5 `tournaments`

Suggested columns: - `id` - `name` - `description` - `format` (initially
single elimination) - `status` (`draft`, `in_progress`, `completed`,
`canceled`) - `start_date` - `created_at` - `updated_at`

### 5.6 `tournament_participants`

Suggested columns: - `id` - `tournament_id` - `player_id` - `seed` -
`final_position`

Add a unique constraint on `(tournament_id, player_id)`.

### 5.7 `achievements`

Suggested columns: - `id` - `name` - `description` - `icon` -
`criteria_type` - `criteria_value` - `is_active`

### 5.8 `player_achievements`

Suggested columns: - `id` - `player_id` - `achievement_id` -
`awarded_at` - `awarded_by` - `notes`

Prevent duplicate awards where appropriate with a unique constraint.

### 5.9 `audit_logs`

Suggested columns: - `id` - `actor_id` - `action` - `entity_type` -
`entity_id` - `before_data` (JSON) - `after_data` (JSON) - `created_at`

Record important admin operations, especially match creation,
correction, cancellation, player deactivation, tournament changes, and
achievement awards.

### Database implementation notes

-   Use UUIDs for entity IDs.
-   Use foreign keys and indexes for frequently queried relationships.
-   Add indexes for match date, player IDs, tournament IDs, and
    rating-history lookups.
-   Use SQLAlchemy 2.x typed mappings.
-   Use Alembic from the beginning; do not rely on `create_all()` as the
    production schema management strategy.
-   Keep the database URL in environment variables.
-   Local example: `sqlite:///./badminton.db`.
-   Production example: Supabase PostgreSQL connection string stored
    only in backend environment variables.
-   Configure SQLite foreign-key enforcement.
-   Use a persistent production database. Do not store production data
    on an ephemeral deployment filesystem.

## 6. Elo rating specification

Implement and test this as a standalone Python module before connecting
it to the database.

### 6.1 Formula

For player A:

\[ E_A = `\frac{1}{1 + 10^{(R_B-R_A)/400}}`{=tex} \]

For player B:

\[ E_B = 1-E_A \]

Actual score: - Winner: `1` - Loser: `0`

Rating update:

\[ R'\_A = R_A + K(S_A-E_A) \]

Initial settings: - Starting rating: 1500 - K-factor: 32 - Rating scale
divisor: 400

### 6.2 Important implementation rules

1.  Use both players' ratings from immediately before the match.
2.  Calculate one symmetric integer rating delta and apply `+delta` to
    the winner and `-delta` to the loser. This keeps the total rating
    points conserved.
3.  For equal 1500 ratings, the winner gains 16 and the loser loses 16.
4.  Do not update ratings for canceled or disputed matches.
5.  Do not process the same match twice.
6.  A tournament match uses exactly the same Elo rules.
7.  Do not allow an admin to manually edit a rating.
8.  Store each player's old rating, new rating, and rating change in
    `rating_history`.

### 6.3 Match correction and replay

Correcting an old match can change the ratings of later matches.
Therefore:

-   Do not simply reverse the old match's rating delta from the current
    rating.
-   Recalculate affected match results in chronological order, starting
    from the earliest affected point.
-   Rebuild the affected rating-history records and update
    current/highest ratings in a single transaction.
-   Preserve an audit log describing the correction and the previous
    result.
-   Add automated tests for corrections and replay before enabling the
    admin correction UI.

## 7. Authentication and authorization

Use Supabase Auth for the single admin account.

### Login flow

1.  Admin signs in through Supabase Auth using email and password.
2.  Frontend receives the Supabase access token.
3.  Frontend sends the token in the `Authorization: Bearer <token>`
    header for admin API requests.
4.  FastAPI validates the token.
5.  Backend checks that the authenticated user is authorized as an
    admin.
6.  Only then may the request perform a write operation.

### Security requirements

-   No public sign-up page.
-   Create the admin account manually in Supabase.
-   Keep an explicit admin allowlist or an admin-role mapping controlled
    by the backend.
-   Do not trust a role supplied by the browser.
-   Do not put Supabase service-role credentials in `NEXT_PUBLIC_*`
    variables.
-   Public GET endpoints must expose only information intended for the
    group.
-   Protect admin routes in both frontend navigation and backend
    authorization.
-   Add basic request validation and sensible rate limits for
    authentication-sensitive endpoints.

For local development, document how to configure authentication. If
Supabase Auth is not configured yet, use a clearly isolated
development-only authentication stub; never ship that stub to
production.

**Acceptance criteria** - Frontend starts locally. - Backend starts

**Tasks** - Configure SQLAlchemy 2.x. - Configure SQLite for local

**Acceptance criteria** - Alembic can create the database from an empty

work. - Tests can create and clean up a test database. - No business
logic is placed in route handlers.

### Phase 2 --- Elo engine

**Tasks** - Implement pure Elo calculation functions. - Add unit tests
for equal ratings, unequal ratings, both winner directions, and integer
rounding. - Implement match processing in a transaction. - Persist
rating history. - Prevent duplicate processing. - Implement
chronological replay for corrected results.

**Acceptance criteria** - Equal 1500 ratings produce +16 / -16. - Winner
gains rating and loser loses rating. - The sum of both players' rating
changes is zero. - Canceled/disputed matches do not change ratings. -
Duplicate processing is rejected safely. - Correction replay produces
the same result as recalculating all matches from scratch.

### Phase 3 --- Core backend APIs

**Tasks** - Implement player CRUD service and endpoints. - Implement
match creation/list/detail endpoints. - Implement current leaderboard. -
Implement player match history and rating history. - Add pagination and
filtering. - Add API tests.

**Acceptance criteria** - Public GET endpoints work without login. -
Write endpoints reject unauthenticated/non-admin users. - Match

### Phase 4 --- Public frontend

**Tasks** - Build dashboard. - Build leaderboard. - Build player

**Acceptance criteria** - All public pages work on desktop and mobile. -
No page uses hardcoded mock data after API integration. -
Empty/loading/error states are present. - Visitors do not need an
account.

### Phase 5 --- Admin panel and authentication

**Tasks** - Integrate Supabase Auth. - Configure the single admin
account. - Implement backend token verification and admin
authorization. - Build admin dashboard. - Build player and match
management. - Add audit logging. - Test every write route with both

**Acceptance criteria** - Admin can sign in and manage data. - Public
visitors cannot write data even if they manually call the API. - Admin
credentials and service keys are not exposed in frontend bundles. -
Match corrections trigger rating replay.

### Phase 6 --- Tournaments, monthly rankings, achievements

**Tasks** - Implement single-elimination tournament creation. - Add
participants and generate brackets. - Record tournament match results
through the same match service. - Implement monthly ranking snapshots. -
Implement achievement definitions and awards. - Build tournament and
achievement pages.

**Acceptance criteria** - Tournament results use normal Elo rules. -
Monthly snapshots do not reset ratings. - Bracket progression is

### Phase 7 --- Deployment and production checks

**Tasks** - Create Supabase PostgreSQL database. - Configure production
database URL. - Run Alembic migrations against PostgreSQL. - Deploy
FastAPI backend. - Deploy Next.js frontend. - Configure environment
variables and CORS. - Configure production Supabase Auth redirect
URLs. - Test backup/export and recovery process.

**Acceptance criteria** - Production data persists across deploys and
restarts. - Public pages work through the shareable URL. - Admin login
and authorization work in production. - No secrets are exposed in
browser code or Git. - A database backup/export can be produced and
restored.

## 11. Testing strategy

At minimum, write tests for:

### Elo

-   Equal ratings.
-   Stronger player wins.
-   Weaker player wins.
-   Winner/loser symmetry.
-   Integer rounding.
-   Zero-sum rating change.

### Matches

-   Valid match creation.
-   Reject player versus themselves.
-   Reject a winner who is not a participant.
-   Canceled match does not change rating.
-   Disputed match does not change rating.
-   Duplicate processing is prevented.
-   Correcting a past match replays later ratings correctly.

### Authorization

-   Public can read public endpoints.
-   Anonymous visitor cannot create a player or match.
-   Authenticated non-admin cannot write.
-   Admin can perform authorized operations.
-   Invalid/expired tokens are rejected.

### Tournaments and statistics

-   Bracket generation for different participant counts.
-   Match advancement.
-   Head-to-head totals.
-   Monthly snapshot consistency.
-   Achievement duplicate prevention.

## 15. Definition of done

The first production release is complete when:

-   [ ] Anyone with the link can view the leaderboard and match history.
-   [ ] Only the admin can create or modify records.
-   [ ] Admin authentication is verified by the backend.
-   [ ] Players can be created and deactivated.
-   [ ] Match results update both players' Elo ratings correctly.
-   [ ] Duplicate match processing is prevented.
-   [ ] Match corrections trigger chronological rating replay.
-   [ ] Player profiles show rating and match history.
-   [ ] The app works on mobile and desktop.
-   [ ] Production uses persistent PostgreSQL storage.
-   [ ] Secrets are not committed or exposed to the browser.
-   [ ] Database migrations and backup/export steps are documented.
-   [ ] Automated tests cover Elo, match processing, and authorization.

**Final principle:** correctness of match processing and rating history
is more important than visual polish. Build the Elo and match-processing
backend first, test it thoroughly, and then build the interface around
it.
